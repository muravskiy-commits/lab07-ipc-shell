3. Part I. Pipes (pipe_basic.c, pipe_processes.c, pipe_no_close.c)

Завдання 1. Створення Pipe (pipe_basic.c)
Виклик pipe(pipefd) створює односпрямований буфер у пам'яті ядра та повертає два файлові дескриптори:
- pipefd[0] — read end (кінець для читання даних із каналу, зазвичай fd 3);
- pipefd[1] — write end (кінець для запису даних у канал, зазвичай fd 4).

Відповіді на питання:
1. Чи є pipe звичайним файлом (regular file)? Ні, анонімний pipe — це об'єкт IPC в оперативній пам'яті ядра (кільцевий буфер), який не має імені у файловій системі та не підтримує операцію lseek().
2. Чому до pipe можна застосовувати read() і write()? Завдяки уніфікованій моделі файлових дескрипторів POSIX/VFS ядро надає однаковий інтерфейс потокового вводу/виводу для файлів, терміналів, сокетів і каналів.
3. Чому pipe() повертає два файлові дескриптори? Оскільки анонімний канал є односпрямованим (unidirectional): один дескриптор відкритий лише на запис, а інший — лише на читання.

Завдання 2 та 3. Pipe між процесами та умова EOF (pipe_processes.c, pipe_no_close.c)

Карта дескрипторів після fork() та після закриття зайвих кінців:
Одразу після fork():
- Parent: fd 3 -> Pipe Read, fd 4 -> Pipe Write
- Child:  fd 3 -> Pipe Read, fd 4 -> Pipe Write

Після налаштування напрямку передачі (Parent -> Child):
- Parent: close(pipefd[0]), залишає відкритим лише fd 4 -> Pipe Write
- Child:  close(pipefd[1]), залишає відкритим лише fd 3 -> Pipe Read

Експеримент із незакритим дескриптором (pipe_no_close.c):
Якщо у читаючому процесі (або у батьківському процесі після завершення запису) не закрити write end (pipefd[1]), цикл while ((n = read(pipefd[0], ...)) > 0) після вичитування всіх даних заблокується назавжди замість виходу з циклу.
Причина: порожній буфер pipe не означає EOF (End of File). Ядро повертає read() == 0 (EOF) лише тоді, коли одночасно виконуються дві умови:
1. буфер каналу порожній;
2. усі без винятку файлові дескриптори, що посилаються на write end цього каналу в усіх процесах, закриті.

Аналіз через strace (-e trace=pipe,pipe2,clone,fork,vfork,read,write,close,wait4 ./pipe_processes):
pipe2([3, 4], 0)                       = 0
clone(child_stack=NULL, ...)           = 5412
close(3)                               = 0
write(4, "Message from parent\n", 20)  = 20
close(4)                               = 0
[pid 5412] close(4)                    = 0
[pid 5412] read(3, "Message from parent\n", 127) = 20
[pid 5412] close(3)                    = 0
wait4(5412, NULL, 0, NULL)             = 5412

4. Part II. Redirection & Pipeline (dup2_output.c, redirect_exec.c, pipeline.c)

Завдання 4 та 5. Перенаправлення через dup2() (dup2_output.c, redirect_exec.c)
Системний виклик dup2(fd, STDOUT_FILENO) закриває поточний дескриптор 1 (термінал) і змушує його посилатися на той самий відкритий файл у таблиці ядра, що й fd (redirected.txt або ls-output.txt).

Карта дескрипторів до і після dup2():
До dup2():
- fd 1 -> /dev/pts/0 (Terminal)
- fd 3 -> redirected.txt

Після dup2(fd, 1) та close(fd):
- fd 1 -> redirected.txt
- fd 3 -> закритий

Після цього виклик printf() або запуск зовнішньої утиліти ls -l через execvp() записує весь стандартний вивід безпосередньо у файл, оскільки відкриті файлові дескриптори зберігаються після виклику execvp().

Завдання 6. Конвеєр ls -l | wc -l (pipeline.c)

Архітектура та карта дескрипторів pipeline:
1. Parent викликає pipe(pipefd) (fd 3 = read, fd 4 = write) та створює два дочірні процеси.
2. Child 1 (виробник даних): викликає dup2(pipefd[1], STDOUT_FILENO), закриває fd 3 та fd 4 і запускає execvp("ls", ...). Його fd 1 тепер вказує на Pipe Write.
3. Child 2 (споживач даних): викликає dup2(pipefd[0], STDIN_FILENO), закриває fd 3 та fd 4 і запускає execvp("wc", ...). Його fd 0 тепер вказує на Pipe Read.
4. Parent закриває обидва кінці каналу (close(pipefd[0]); close(pipefd[1]);) і викликає waitpid() для обох дітей. Якби parent не закрив pipefd[1], утиліта wc -l ніколи б не отримала EOF і зависла б.

5. Part III. Signals (signal_int.c, signal_parent_child.c)

Результати експериментів із сигналами:
1. signal_int.c: при натисканні Ctrl+C термінал надсилає активному процесу сигнал SIGINT. Завдяки встановленому через sigaction() обробнику handle_sigint процес не завершується, а виводить "\nSIGINT received\n" через async-signal-safe функцію write().
2. signal_parent_child.c: батьківський процес через 2 секунди викликає kill(pid, SIGTERM). За замовчуванням SIGTERM завершує процес, але після встановлення власного обробника дочірній процес перехоплює сигнал, встановлює прапорець sig_atomic_t і коректно завершує роботу зі статусом 0.
3. Експеримент із kill -KILL PID (SIGKILL): процес завершується миттєво повідомленням "Killed", навіть якщо в ньому встановлені обробники сигналів.

Порівняння SIGINT, SIGTERM та SIGKILL:
- SIGINT (номер 2): сигнал переривання з клавіатури (Ctrl+C); може бути перехоплений або проігнорований процесом.
- SIGTERM (номер 15): стандартний запит на коректне завершення програми; може бути перехоплений для звільнення ресурсів перед виходом.
- SIGKILL (номер 9): примусове знищення процесу безпосередньо ядром ОС; не може бути перехоплений, заблокований чи проігнорований (гарантує адміністратору та ОС можливість зупинити будь-який завислий процес).

6. Part IV. Mini-Shell (mini_shell.c)

Архітектура реалізованої оболонки:
1. Головний цикл зчитує рядок командою fgets(), перевіряє наявність символу конвеєра '|' або перенаправлення виводу '>'.
2. Вбудовані команди (exit, cd) виконуються безпосередньо в батьківському процесі оболонки.
3. Зовнішні команди запускаються за схемою fork() -> налаштування сигналів і dup2() у дочірньому процесі -> execvp() -> очікування у батьківському процесі через waitpid().

Чому cd має бути вбудованою командою (built-in) оболонки?
Поточний робочий каталог (current working directory) є атрибутом конкретного процесу. Якби оболонка викликала fork() і виконала chdir() у дочірньому процесі, робочий каталог змінився б лише для дитини, яка одразу після цього завершується, а сама оболонка залишилася б у попередньому каталозі.

Результати тестування всіх функцій mini_shell:
- Перенаправлення виводу (myshell> echo hello > output.txt): у дочірньому процесі файл output.txt відкривається з прапорцями O_WRONLY | O_CREAT | O_TRUNC, підключається до STDOUT_FILENO через dup2(), після чого запускається echo; файл output.txt містить рядок "hello".
- Конвеєр (myshell> ls -l | wc -l): створюється pipe, два дочірні процеси з'єднуються через dup2() (stdout першого -> pipe -> stdin другого), оболонка закриває обидва кінці каналу і виводить кількість рядків списку файлів.
- Обробка Ctrl+C (myshell> sleep 30 -> Ctrl+C): сама оболонка встановлює SIG_IGN для SIGINT, а кожен дочірній процес перед execvp() повертає SIG_DFL. Тому натискання Ctrl+C перериває лише активну команду sleep 30, а оболонка залишається живою і знову виводить запрошення "myshell> ".

Короткий аналіз strace для mini_shell (на прикладі echo hello > output.txt та ls | wc -l):
- Для echo hello > output.txt: clone() створює дочірній процес, у ньому викликається openat(AT_FDCWD, "output.txt", O_WRONLY|O_CREAT|O_TRUNC, 0644) = 3, далі dup2(3, 1) = 1, close(3) = 0 та execve("/usr/bin/echo", ...), тоді як батьківський процес чекає через wait4().
- Для ls | wc -l: pipe2([3, 4], 0) = 0 створює канал, перший clone() виконує dup2(4, 1), close(3), close(4) та execve("/usr/bin/ls", ...), другий clone() виконує dup2(3, 0), close(3), close(4) та execve("/usr/bin/wc", ...), а батьківський процес закриває fd 3 і fd 4 та виконує два виклики wait4().

7. Відповіді на контрольні питання

1. Що таке IPC? Inter-Process Communication — механізми обміну даними та синхронізації між окремими процесами (pipes, сигнали, сокети, спільна пам'ять).
2. Що створює pipe()? Анонімний односпрямований канал передачі байтів у пам'яті ядра та пару файлових дескрипторів для читання і запису.
3. Що означає pipefd[0]? Файловий дескриптор кінця каналу, призначеного для читання (read end).
4. Що означає pipefd[1]? Файловий дескриптор кінця каналу, призначеного для запису (write end).
5. Чому pipe можна використовувати через read() та write()? Бо в Unix/POSIX усі потокові ресурси представлені через уніфіковану абстракцію файлових дескрипторів.
6. Які descriptors отримує child після fork()? Точну копію всіх відкритих файлових дескрипторів батьківського процесу (включно з 0, 1, 2 та обома кінцями pipe).
7. Чому потрібно закривати unused pipe ends? Щоб уникнути витоку дескрипторів і забезпечити коректне отримання EOF читачем після завершення роботи письменника.
8. Коли read() із pipe повертає EOF? Коли буфер каналу порожній і всі дескриптори запису (write ends) у всіх процесах закриті.
9. Що станеться, якщо parent залишить write end відкритим? Читаючий дочірній процес після вичитування даних назавжди заблокується у виклику read(), очікуючи нових байтів.
10. Що робить dup2()? Дублює відкритий файловий дескриптор у вказаний номер дескриптора, попередньо закриваючи його, якщо він був відкритий.
11. Як реалізується >? Відкриттям цільового файлу через open(), підміною дескриптора 1 (STDOUT_FILENO) на дескриптор файлу через dup2() перед викликом exec().
12. Чому program не повинна знати, що її stdout redirected? Бо програма завжди пише у фіксований дескриптор 1, а підміна реального ресурсу за цим номером відбувається прозоро на рівні таблиці дескрипторів ядра.
13. Як побудувати program1 | program2? Створити pipe(), породити два процеси через fork(), у першому підключити stdout до pipefd[1], у другому підключити stdin до pipefd[0], закрити зайві дескриптори та викликати exec().
14. Який descriptor першої program підключається до pipe? STDOUT_FILENO (fd 1) підключається до pipefd[1] (write end).
15. Який descriptor другої program підключається до pipe? STDIN_FILENO (fd 0) підключається до pipefd[0] (read end).
16. Що таке signal? Асинхронне програмне переривання (повідомлення), яке ядро або інший процес надсилає процесу для сповіщення про певну подію.
17. Чим signal відрізняється від pipe? Signal передає лише номер події (сповіщення), тоді як pipe передає потік довільних байтів даних.
18. Що робить kill()? Системний виклик, який надсилає вказаний сигнал процесу або групі процесів за їхнім PID.
19. Чим SIGTERM відрізняється від SIGKILL? SIGTERM можна перехопити або проігнорувати для плавного завершення, а SIGKILL обробляється виключно ядром і негайно знищує процес.
20. Чому не можна catch SIGKILL? Щоб ядро ОС завжди мало безумовний механізм примусового завершення будь-якого процесу, навіть якщо він завис або заблокував усі інші сигнали.
21. Що таке SIGINT? Сигнал переривання (Interrupt), який термінал надсилає активній групі процесів при натисканні Ctrl+C.
22. Чому printf() не підходить для signal handler? Оскільки printf() використовує внутрішні блокування (mutex) буфера stdio; якщо сигнал перерве програму під час іншого виклику printf(), повторний виклик у обробнику спричинить deadlock.
23. Що таке async-signal-safe function? Функція (наприклад, write(), _exit()), яку безпечно викликати всередині обробника сигналу без ризику пошкодження внутрішніх структур даних чи взаємного блокування.
24. Чому shell є user-space program, а не частиною kernel? Це забезпечує безпеку, стабільність та гнучкість: збій оболонки не призводить до краху ядра, а користувач може вільно вибирати або змінювати оболонки (bash, zsh, mini_shell).
25. Що робить fork() у shell? Створює копію процесу оболонки (дочірній процес), у якому буде запущена зовнішня команда без знищення самої оболонки.
26. Що робить exec()? Замінює образ програми в поточному дочірньому процесі на виконуваний файл вказаної команди.
27. Для чого потрібен waitpid()? Щоб оболонка призупинилася до завершення foreground-команди і зібрала її статус виходу, не створюючи zombie-процесів.
28. Чому cd повинен бути shell built-in? Бо зміна робочого каталогу через chdir() впливає лише на процес, який її викликав; виконання cd у дочірньому процесі не змінило б каталог самої оболонки.
29. Чому exit повинен виконуватися самим shell? Бо мета команди exit — завершити головний цикл процесу самої оболонки, а не тимчасового дочірнього процесу.
30. Чому system() не підходить для цієї лабораторної? Оскільки system() запускає системний /bin/sh -c, приховуючи від студента реальну роботу з fork, exec, pipe, dup2 та сигналами.
31. Що відбувається з file descriptors після exec()? Відкриті файлові дескриптори (якщо для них не встановлено прапорець FD_CLOEXEC) зберігаються у новому образі програми — саме на цьому базується перенаправлення вводу/виводу.
32. Як fork(), pipe() та dup2() разом створюють pipeline? pipe() створює буфер ядра, fork() розмножує процеси зі спільними дескрипторами каналу, а dup2() підміняє їхні стандартні потоки 1 і 0 на відповідні кінці каналу перед exec().
33. Чому pipeline processes можуть виконуватися concurrently? Обидва дочірні процеси запускаються планувальником ОС одночасно; ядро автоматично синхронізує їх через буфер pipe (призупиняє читача, якщо канал порожній, і письменника, якщо буфер заповнений).
34. Що відбувається, якщо reader pipe завершився, а writer продовжує писати? Ядро надсилає процесу-письменнику сигнал SIGPIPE (який за замовчуванням завершує його), а виклик write() повертає помилку EPIPE.
35. Які ресурси повинен закривати parent після створення pipeline? Обидва файлові дескриптори каналу (pipefd[0] та pipefd[1]), оскільки батьківська оболонка сама не бере участі в обміні даними через цей канал.

8. Висновок
У фінальній лабораторній роботі всі ключові механізми операційної системи — створення процесів, керування файловими дескрипторами, анонімні канали, дублювання потоків та обробка сигналів — були об'єднані в єдину робочу програму mini_shell. На практиці доведено, як саме командна оболонка керує життєвим циклом команд, забезпечує перенаправлення потоків у файли та будує конвеєри обробки даних між незалежними програмами.
